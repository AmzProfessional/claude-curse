# Модуль 5: Логіка MVP — Від ідеї до плану

> **Тривалість:** 25 хв теорія + 35 хв практика
> **Результат:** PRD документ + технічний план для свого MVP

---

## Теорія

### Що таке MVP і навіщо

**MVP (Minimum Viable Product)** — мінімально життєздатний продукт. Це найпростіша версія продукту, яка вже вирішує проблему користувача.

```
Ідея → [MVP] → Тестування → Зворотній зв'язок → Покращення
         ↑
    Ми тут зупиняємось
    і перевіряємо чи це 
    комусь потрібно
```

![[Що таке MVP і навіщо.png]]

**Приклад:**
- **Ідея:** Сервіс бронювання переговорок в офісі
- **НЕ MVP:** Додаток з авторизацією, календарем, сповіщеннями, інтеграцією з Google Calendar, аналітикою використання, адмін-панеллю
- **MVP:** Веб-сторінка де видно вільні слоти та можна забронювати кімнату на email

### Найпоширеніша помилка

> "Я хочу щоб мій MVP мав ВСЕ."

Це вже не MVP. Це повноцінний продукт який ніколи не буде закінчений.

**Правило:** Якщо ти не можеш описати свій MVP в одному реченні — він занадто складний.

- ✅ "Сторінка де можна забронювати переговорку"
- ✅ "Бот який нагадує про дедлайни"
- ✅ "Дешборд з продажами за місяць"
- ❌ "Повна CRM-система з аналітикою та інтеграціями"

### PRD — Product Requirements Document

PRD — це документ який описує ЩО ми створюємо і ЧОМУ, перед тим як починати.

**Структура PRD для вайбкодингу:**

```markdown
# Назва проєкту

## Проблема
Яку проблему вирішуємо? (2-3 речення)

## Рішення  
Як саме вирішуємо? (2-3 речення)

## Цільова аудиторія
Хто буде використовувати? (конкретна група людей)

## Ключові функції (максимум 3-5)
1. Функція А — що робить
2. Функція Б — що робить
3. Функція В — що робить

## User Stories
- Як [хто], я хочу [що зробити], щоб [навіщо]
- Як [хто], я хочу [що зробити], щоб [навіщо]
- Як [хто], я хочу [що зробити], щоб [навіщо]

## Що НЕ входить в MVP
- Те, що хотілось би, але зробимо пізніше
- Те, без чого MVP буде працювати

## Метрика успіху
Як зрозуміємо що MVP працює? (1 конкретна метрика)
```

**Живий приклад — PRD для Amazon Competitor Tracker:**

```markdown
# Amazon Competitor Tracker

## Проблема
Аналітики витрачають 2+ години щодня на ручний моніторинг 50 конкурентних 
лістингів на Amazon. Відкривають кожну сторінку, записують ціни, BSR, 
відгуки в Excel. Порівнюють з вчорашніми вручну. Аномалії пропускають.

## Рішення
Веб-дешборд який автоматично збирає дані 50 конкурентів щовечора, 
порівнює з попередніми періодами, знаходить аномалії та генерує звіти.

## Цільова аудиторія
Аналітики та менеджери e-commerce команди (5-10 людей).

## Ключові функції (MVP)
1. Таблиця конкурентів — ціна, BSR, revenue, зміна за день
2. Порівняння періодів — вчора, тиждень, місяць
3. Аномалії — автоматичне виявлення різких змін

## User Stories
- Як аналітик, я хочу бачити зміни за ніч, щоб зранку знати що відбулось
- Як менеджер, я хочу порівняти цей тиждень з минулим, щоб розуміти тренд
- Як аналітик, я хочу бачити аномалії автоматично, щоб не пропустити важливе

## Що НЕ входить в MVP
- Авторизація (поки внутрішній інструмент, доступ по посиланню)
- Автоматичний збір даних (поки завантажуємо CSV вручну)
- Сповіщення в Telegram (додамо в [[08-automation|модулі 8]])
- Красивий дизайн (працює = достатньо)

## Метрика успіху
Аналітики починають використовувати дешборд замість ручного моніторингу.
Конкретно: 3 з 5 аналітиків відкривають дешборд щоранку протягом тижня.
```

### User Stories — як думати про користувача

User Story — це опис функції з точки зору користувача:

> **Як** [хто я], **я хочу** [що зробити], **щоб** [навіщо]

**Приклади:**
- Як менеджер, я хочу бачити вільні переговорки, щоб швидко забронювати кімнату
- Як клієнт, я хочу фільтрувати товари за ціною, щоб знайти щось у своєму бюджеті
- Як адмін, я хочу бачити статистику замовлень, щоб розуміти що продається найкраще

**Чому це важливо для вайбкодингу:**
User stories стають промптами! Кожна user story — це окрема задача для AI.

### Вибір стеку технологій

"Стек" — це набір технологій для проєкту. AI допоможе обрати, але тобі корисно знати варіанти:

| Тип проєкту | Рекомендований стек | Складність |
|-------------|-------------------|------------|
| Статичний лендінг | HTML + CSS | Найпростіше |
| Сайт з кількома сторінками | HTML + CSS + JS | Просто |
| Веб-додаток | Next.js + Tailwind | Середньо |
| Додаток з базою даних | Next.js + Supabase | Середньо+ |
| Бот | Python + API платформи | Середньо |
| Автоматизація | Python або n8n | Залежить від задачі |

**Для цього курсу рекомендовано:** Next.js + Tailwind CSS + Supabase ([[06-frontend|модулі 6]]-[[09-deploy|9]])

### Планування через AI

Claude Code може допомогти спланувати проєкт. Є два підходи:

#### Підхід 1: Простий промпт для планування

```
Я хочу створити MVP [опис]. Допоможи мені:

1. Визначити мінімальний набір функцій
2. Запропонувати структуру проєкту
3. Порекомендувати технічний стек
4. Розбити роботу на кроки

Контекст: я новачок, не маю досвіду програмування, 
використовую вайбкодинг з Claude Code.
```

#### Підхід 2: Plan Mode — "спочатку план, потім код"

Claude Code має спеціальний режим планування. Замість того щоб одразу писати код, він спочатку створює детальний план і показує тобі.

**Як використовувати:**
```
Спланируй реалізацію [задача]. Не пиши код — 
спочатку покажи план: які файли створити, 
в якому порядку, яка буде структура.
```

Claude покаже план → ти переглянеш → скажеш "ок, реалізуй" або "зміни ось це".

**Чому це працює:**
- AI допускає менше помилок коли спочатку думає, потім пише
- Ти бачиш план до того як код написаний — легше виправити напрямок
- Менше переробок — план фіксує архітектуру до початку роботи

**Коли використовувати Plan Mode:**
- Нова сторінка або великий компонент
- Задача яка торкається 3+ файлів
- Ти не впевнений як підійти до задачі

**Коли НЕ потрібен:**
- Проста правка в одному файлі
- "Зміни колір кнопки на синій"

## Практика

### Завдання 1: Обери свій MVP (10 хв)

Обери проєкт для курсу (цей MVP ти будеш розвивати до кінця курсу):

**Наскрізний приклад курсу — Amazon Competitor Tracker:**
Якщо не знаєш що обрати — бери його. Ми будемо показувати приклади на ньому через весь курс, тому тобі буде легше йти в ногу.

**Або обери свій варіант:**
- **А)** Дешборд аналітики для своєї ніші (eBay, Etsy, свій ринок)
- **Б)** Внутрішній інструмент для команди — автоматизація звітів, моніторинг
- **В)** Інструмент для клієнтів — калькулятор, порівняльник, трекер
- **Г)** Свій варіант — обговори з інструктором

**Критерії хорошого вибору:**
- Вирішує реальну проблему (хоча б твою)
- Можна описати в одному реченні
- 3-5 ключових функцій
- Результат можна побачити в браузері

### Завдання 2: Напиши PRD (15 хв)

1. Створи файл `PRD.md` в папці свого проєкту
2. Заповни шаблон PRD
3. Покажи PRD Claude Code та попроси feedback:
   ```
   Прочитай мій PRD.md. Дай feedback:
   - Чи зрозуміла проблема?
   - Чи достатньо конкретні user stories?
   - Чи не занадто багато функцій для MVP?
   - Що можна прибрати без втрати цінності?
   ```

### Завдання 3: Технічний план (10 хв)

Попроси Claude Code створити план:
```
На основі PRD.md створи технічний план реалізації.
Потрібно:
1. Структура проєкту
2. Список сторінок з описом що на кожній
3. Порядок реалізації
4. Які зовнішні сервіси або API будуть потрібні

Стек: Next.js + Tailwind CSS.
Рівень: для новачка через вайбкодинг.
```

Збережи результат у файл `PLAN.md`.

## Питання для самоперевірки

1. MVP з авторизацією, дешбордом, адмін-панеллю, сповіщеннями, темною темою і мобільним додатком. Це MVP?

2. User story: "Як аналітик, я хочу бачити зміни за ніч, щоб зранку знати що відбулось". Як це перетворюється в промпт для AI?

3. PRD для Amazon Competitor Tracker описує 3 ключових функції. Навіщо писати PRD якщо можна просто почати кодити?

4. Метрика успіху MVP: "3 з 5 аналітиків відкривають дешборд щоранку". Чому це краще ніж "зробити гарний дешборд"?
