# Модуль 2A: Бекапи та версії — Страховка для вайбкодера

> **Тривалість:** 15 хв теорія + 15 хв практика
> **Результат:** Навичка зберігати прогрес та відкочуватись

## Теорія

### Навіщо бекапи — реальна історія

Уяви: ти 3 години будував дешборд. Все працювало. Потім попросив AI "трохи покращити стилі" — і все зламалось. Ти просиш виправити — стає гірше. Паніка. Відчай. Ctrl+Z не допомагає, бо зміни в 15 файлах.

Якщо ти робив коміти — просто `git checkout` і ти повертаєшся в стан "3 години тому, коли все працювало". Якщо не робив — починай з нуля. Не будь тим хлопцем. Роби коміти.

### Коли зберігати (комітити)

**Золоте правило:** якщо ти подивився в браузер і сказав "о, працює!" — одразу коміть.

```
✅ КОМІТИТИ коли:                    ❌ НЕ КОМІТИТИ коли:
─────────────────                    ────────────────────
Щось запрацювало                     Код наполовину написаний
Додав нову секцію/сторінку           Є очевидні помилки
Виправив баг                         Середина рефакторингу
Перед великою зміною                 Тимчасовий тестовий код
Закінчив логічний блок роботи        Console.log на кожному рядку
Перед "а давай спробую інакше"       
```

### Як правильно комітити

```bash
# 1. Подивись що змінилось
git status

# 2. Перевір зміни (не комітиш щось зайве?)
git diff

# 3. Додай файли
git add .

# 4. Опиши ЩО ти зробив (для себе з майбутнього)
git commit -m "Додав секцію порівняння тижнів з графіком"
```

**Хороші повідомлення комітів:**
```
✅ "Додав форму фільтрації по датах"
✅ "Виправив баг з завантаженням даних конкурентів"
✅ "Секція hero — фінальна версія"
✅ "Перед рефакторингом навігації — все працює"

❌ "fix"
❌ "update"  
❌ "зміни"
❌ "asdfgh"
```

Повідомлення коміту — це записка для себе з майбутнього. Через тиждень "fix" тобі нічого не скаже, а "Виправив баг де ціни показувались в центах замість доларів" — скаже все.

### Коміти — англійською мовою

> **Важливо:** В курсі ми пишемо коміти українською для зрозумілості. В реальній роботі — **завжди англійською.**

**Чому англійська:**
- Проєкт можуть передати інженерам — вони можуть не знати української
- Git-історія — це документація, і вона має бути зрозуміла всім
- Англійська — стандарт індустрії, навіть в українських компаніях
- Інструменти (GitHub, CI/CD) краще працюють з латиницею

**Формат:** дієслово в наказовому способі + що змінив. Коротко. Без крапки.

```
✅ ДОБРІ КОМІТИ:
───────────────
Add hero section with CTA button
Fix price display bug in competitor table
Update weekly comparison chart layout
Remove unused API endpoint
Refactor data fetching to use Supabase
Add date filter to dashboard
Fix mobile navigation menu
Style product cards with shadows and rounded corners

❌ ПОГАНІ КОМІТИ:
────────────────
fix                          ← що саме?
update                       ← що оновив?
changes                      ← дякую, дуже інформативно
WIP                          ← не комітити недороблене
asdfjkl                      ← ти серйозно?
Fixed the thing              ← яку thing?
Made it work                 ← що саме?
```

### Шпаргалка комітів для типових ситуацій

```bash
# Додав щось нове
git commit -m "Add pricing section to landing page"
git commit -m "Add competitor data export to CSV"
git commit -m "Add Telegram bot /report command"

# Виправив баг
git commit -m "Fix broken navigation links"
git commit -m "Fix data not loading on dashboard"
git commit -m "Fix chart rendering on mobile"

# Змінив/покращив існуюче
git commit -m "Update hero section copy and colors"
git commit -m "Improve weekly comparison accuracy"
git commit -m "Refactor API calls to reduce load time"

# Видалив непотрібне
git commit -m "Remove deprecated analytics endpoint"
git commit -m "Remove test data from production build"

# Перед експериментом
git commit -m "Stable version before layout refactor"
git commit -m "Working state before adding dark theme"

# Стилі
git commit -m "Style competitor cards with brand colors"
git commit -m "Make dashboard responsive for mobile"
```

**Підказка:** не потрібно запам'ятовувати — попроси Claude Code: *"зроби коміт з описом англійською"* — він сам напише правильне повідомлення.

### Бранчі — паралельні версії

**Бранч (branch)** — це окрема копія проєкту де ти можеш експериментувати, не зламавши основну версію.

```
main (стабільна версія)
  │
  ├── feature/new-dashboard ← експеримент з новим дизайном
  │     │
  │     ├── Спрацювало? → merge в main
  │     └── Не сподобалось? → видалив бранч, main не постраждав
  │
  └── продовжуєш працювати на main
```

**Коли створювати бранч:**
```bash
# Перед великою зміною яка може все зламати
git checkout -b experiment/new-layout

# Попрацював, не сподобалось? Повернувся на main
git checkout main

# Сподобалось? Merge
git merge experiment/new-layout
```

**Правило:** Якщо зміна торкається більше 3-х файлів і ти не впевнений в результаті — зроби бранч.

### Відкат — коли все зламалось

Ситуацій коли потрібен відкат кілька:

#### Ситуація 1: Останній коміт все зламав

```bash
# Подивись що було в останньому коміті
git log --oneline -5

# Відкотити ОДИН коміт (зміни залишаться в файлах, але "розкомічені")
git reset --soft HEAD~1

# Або повний відкат (зміни зникнуть повністю)
git reset --hard HEAD~1
```

#### Ситуація 2: Хочу повернутись до конкретного стану

```bash
# Знайди потрібний коміт
git log --oneline

# Виведе щось типу:
# a1b2c3d Add date filter to dashboard    ← ось цей працював!
# e4f5g6h Refactor navigation (broken)
# h7i8j9k Add weekly comparison section

# Створи бранч від того моменту
git checkout -b restore/working-version a1b2c3d
```

#### Ситуація 3: Один конкретний файл зламався

```bash
# Повернути один файл до стану з останнього коміту
git checkout -- src/components/Header.tsx
```

#### Ситуація 4: AI наробив змін і все зламалось

Не панікуй. Claude Code теж робить помилки. Варіанти (від найшвидшого):

1. **`/rewind` в Claude Code** — відкочує і файли, і розмову. AI "забуває" невдалу спробу — найчистіший варіант
2. **Відкотись через git:** `git checkout .` — повертає ВСІ файли до останнього коміту
3. **Відкотись частково:** `git checkout -- файл.tsx` — тільки один файл

**`/rewind` vs `git checkout .`** — коли що:
- `/rewind` — коли AI зробив помилку і ти хочеш спробувати інший промпт (чистить контекст)
- `git checkout .` — коли ти хочеш повернутись до коміту і продовжити розмову з AI

#### Правило: два рази не вийшло → відкотись

Якщо AI двічі не зміг виправити проблему — **не проси третій раз.** Кожна невдала спроба забруднює контекст розмови, і AI починає працювати ще гірше.

```
Спроба 1: не вийшло → ок, буває
Спроба 2: знову не вийшло → СТОП
Спроба 3: ❌ не роби цього

Замість третьої спроби:
  /rewind → новий, чіткіший промпт
  або
  /clear → почни задачу з нуля
```

### Стратегія бекапів для вайбкодера

```
Ранок:
  └── git commit -m "Stable state — start of work session"
  
Кожні 15-30 хв продуктивної роботи:
  └── git commit -m "Add [що зробив]"

Перед кожним "а давай спробую":
  └── git commit -m "Working state before [експеримент]"
  
Перед деплоєм:
  └── git commit -m "Pre-deploy — all features verified"

Кінець дня:
  └── git push (відправити на GitHub — бекап в хмарі)
```

**GitHub — це твій хмарний бекап.** Навіть якщо ноутбук помре, проєкт збережений. `git push` раз на день — мінімум.

## Практика

### Завдання 1: Комітити як профі (10 хв)

1. Створи тестовий проєкт або відкрий існуючий
2. Зроби 3 зміни, після кожної — коміт з описом **англійською**:
   ```bash
   # Зміна 1
   git add .
   git commit -m "Add heading to home page"
   
   # Зміна 2
   git add .
   git commit -m "Add three feature cards section"
   
   # Зміна 3
   git add .
   git commit -m "Style cards with shadows and rounded corners"
   ```
3. Перевір історію: `git log --oneline`
4. Відкотись на 1 коміт: `git reset --hard HEAD~1`
5. Перевір — картки без стилів! Магія.

### Завдання 2: Бранч для експерименту (5 хв)

1. Створи бранч: `git checkout -b experiment/dark-theme`
2. Попроси Claude Code: "Зроби темну тему для всієї сторінки"
3. Подивись результат
4. Не сподобалось? `git checkout main` — повернувся до світлої
5. Сподобалось? `git checkout main && git merge experiment/dark-theme`

## Шпаргалка

```bash
# ЗБЕРЕГТИ
git add .                          # Підготувати зміни
git commit -m "опис"               # Зберегти версію
git push                           # Відправити в хмару

# ВІДКОТИТИ
git checkout -- файл.tsx           # Один файл до останнього коміту
git checkout .                     # ВСІ файли до останнього коміту  
git reset --soft HEAD~1            # Відмінити коміт (зміни лишаються)
git reset --hard HEAD~1            # Відмінити коміт (зміни зникають)

# БРАНЧ
git checkout -b назва-бранча       # Створити бранч
git checkout main                  # Повернутись на main
git merge назва-бранча             # Об'єднати бранч з main
git branch -d назва-бранча         # Видалити бранч

# ІНФО
git status                         # Що змінилось?
git log --oneline -10              # Останні 10 комітів
git diff                           # Що саме змінилось в файлах?
```
